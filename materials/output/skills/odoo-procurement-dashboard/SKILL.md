  조회 전용(read-only) — 발주나 재고를 만들거나 바꾸지 않는다.

# Odoo 조달 현황 대시보드

## 이 스킬이 있는 이유

서로 다른 3~4개 모델을 조회해 하나의 화면으로 합치는 팬아웃 스킬이다. 두 가지를
붙잡기 위해 존재한다.

**하나, 판정 기준을 고정한다.** "재고 부족이 몇 개죠?"에 어제는 5개, 오늘은 3개로
답하면 그 대시보드는 회의에서 못 쓴다. 부족의 정의는 아래 1단계에 못 박혀 있고,
기준을 바꿔야 한다면 이 파일을 고쳐서 팀 전체에 한 번에 반영한다.

**둘, 수집과 표현을 분리한다.** 이 스킬은 숫자를 모으고 판정만 한다. 차트와
슬라이드는 `pptx` 스킬이 맡는다. 여기에 차트 코드나 문서 서식을 직접 짜 넣으면,
표현 방식이 바뀔 때마다 판정 로직까지 흔들린다.

# 1부. 데이터 수집 (Odoo MCP 3~4회)

호출은 3~4회면 충분하다. 품목마다 따로 부르지 말 것 — 열 품목이면 열 번이 되고,
그 시간만큼 사용자는 빈 화면을 본다.

## 1단계 — 재고 부족 판정

```
mcp__odoo__search_records(
  model="stock.warehouse.orderpoint",
  fields=["product_id", "product_min_qty", "product_max_qty",
          "qty_on_hand", "qty_forecast", "qty_to_order", "warehouse_id"],
  limit=200, order="id asc")
```

한 번이면 된다. `orderpoint.qty_on_hand`는 `product.product.qty_available`과 같은
값이고, `product_id`가 `[1, "[PCB-100] 메인 컨트롤 PCB"]`처럼 품목코드까지 담아
돌려주므로 이름을 얻으려고 `product.product`를 또 부를 필요가 없다.

### 판정 기준 — 이 두 줄은 임의로 바꾸지 않는다

```
부족    ⟺  qty_available < product_min_qty
보충 필요량  =  product_max_qty - qty_available
```

`qty_available`은 위 호출의 `qty_on_hand`를 쓴다.

**경계 케이스: `qty_available == product_min_qty`는 정상으로 본다.** `<`이지
`<=`가 아니다. 이 한 줄이 없으면 같은 데이터로도 사람마다 부족 건수가 달라진다.
다만 딱 재주문점에 걸린 품목은 한 개만 나가도 부족으로 넘어가므로, 부족 건수에는
넣지 않되 "재주문점 도달"로 따로 표시해 주면 실무에서 유용하다. **표시는 하되
집계에는 넣지 않는다** — 이 구분이 흐려지면 위 기준이 무의미해진다.

### `qty_to_order`를 판정에 쓰지 않는 이유

Odoo가 계산해 주는 `qty_to_order`가 있는데 왜 직접 판정하는지 궁금할 것이다.
**`qty_to_order`와 `qty_forecast`는 확정되지 않은 견적 상태 발주서까지 입고 예정으로
쳐 준다.** 실제로 확인된 사례:

| 품목 | 현재고 | 최소 | 예상재고 | Odoo `qty_to_order` |
|---|---|---|---|---|
| PCB-100 | 12 | 30 | 52 | **0** ← 견적 상태 발주 40개를 입고로 계산 |
| CBL-600 | 90 | 150 | 290 | **0** ← 견적 상태 발주 200개를 입고로 계산 |

견적서는 확정하지 않으면 영원히 입고되지 않는다. `qty_to_order`만 믿으면 이런
품목이 부족 목록에서 조용히 사라진다. 그래서 판정은 **실물 현재고**로 하고,
`qty_forecast`는 판정이 아니라 "이미 조치가 걸려 있는가"를 보여주는 참고 열로 쓴다.

### 3단 분류

부족 판정 위에 조치 여부를 얹으면 "지금 뭘 해야 하나"가 바로 보인다.

| 표시 | 조건 | 뜻 |
|---|---|---|
| 🔴 조치 필요 | 부족 & `qty_forecast < product_min_qty` | 아무 대책 없음. 오늘 발주할 대상 |
| 🟡 조치 중 | 부족 & `qty_forecast >= product_min_qty` | 입고 예정이나 견적이 걸려 있음 |
| 🟢 정상 | 부족 아님 | (`==` 경계면 "재주문점 도달"로 부기) |

🟡는 반드시 **무엇이 걸려 있는지**를 함께 적는다 — 확정 발주의 입고 예정인지,
아직 확정 안 된 견적서인지에 따라 안심해도 되는지가 갈린다. 견적서라면 확정을
촉구하는 것이 이 대시보드의 실질적인 결론이 된다.

## 2단계 — 거래처별 발주 현황

```
mcp__odoo__aggregate_records(
  model="purchase.order",
  groupby=["partner_id"],
  aggregates=["__count", "amount_total:sum"],
  order="amount_total:sum desc", limit=100)
```

집계는 서버에 맡긴다. 발주서를 전부 끌어와 직접 더하지 않는다 — 건수가 늘면
그대로 무너진다.

**견적(`draft`) 상태가 이 합계에 섞여 있다는 점을 반드시 밝힌다.** 확정 실적만
필요하면 `domain=[["state", "in", ["purchase", "done"]]]`을 걸고, 어느 쪽이든
대시보드에 기준을 적어 둔다. 이걸 안 적으면 회계 숫자와 안 맞는 이유를 아무도
설명하지 못한다.

월별 추이가 필요하면 `groupby=["date_order:month"]`로 한 번 더 부른다(선택).

## 3단계 — 협력사 현황

```
mcp__odoo__search_records(
  model="res.partner",
  domain=[["supplier_rank", ">", 0]],
  fields=["name", "email", "phone", "is_company", "parent_id"],
  limit=100, order="id asc")
```

이름만 나열하면 패널 하나를 낭비하는 것이다. 2단계 결과와 대조해서 **말이 되는
것**을 뽑는다:

- **발주 이력이 없는 협력사** — 신규 등록 후 아직 거래가 없는 곳. 등록만 하고
  잊힌 협력사를 드러낸다.
- **연락처 결손** — 이메일이나 전화가 비어 있는 곳. 급할 때 연락이 안 된다.
- **거래 집중도** — 상위 3개사 비중. 한 곳이 30%를 넘으면 공급 차질 리스크로 짚는다.

## 4단계 (선택) — 부족 품목의 공급사 연결

🔴 품목이 하나라도 있으면 이것까지 부른다. "무엇이 부족한가"에서 "누구에게 얼마나
발주해야 하는가"로 넘어가는 데 필요한 마지막 조각이다.

```
mcp__odoo__search_records(
  model="product.supplierinfo",
  domain=[["product_tmpl_id", "in", [<부족 품목 id들>]]],
  fields=["product_tmpl_id", "partner_id", "price", "min_qty", "delay"],
  limit=50)
```

`delay`(리드타임)를 반드시 함께 보여준다. 현재고 12개에 리드타임 14일인 품목과
현재고 240개에 리드타임 4일인 품목은 같은 "부족"이 아니다. 급한 순서는 부족
수량이 아니라 **리드타임 대비 잔여 재고**로 정해진다.

# 2부. 표현 (위임)

여기서부터는 이 스킬이 직접 만들지 않는다.

## 5단계 — 산출물 조립

**먼저 pptx 스킬이 실제로 설치돼 있는지 확인한다.** 없는 스킬을 부르면 실패하고,
사용자는 대시보드 대신 에러를 본다.

### pptx 스킬이 있을 때 — 기본 경로

슬라이드 조립과 차트 생성을 **모두** pptx에 넘긴다. 넘길 내용은 아래 「pptx에
무엇을 넘기는가」를 따른다. 표지 / 재고 부족 / 발주 현황 / 협력사 / 결론 5장
구성이 기본이다.

### pptx 스킬이 없을 때 — 대안 경로

**현재 이 프로젝트 환경이 여기 해당한다.** 이 경우 **차트는 만들지 않는다.**
차트 생성 경로가 pptx 하나뿐이므로, 없으면 그림 없는 표로 간다. 다른 도구로
차트를 급조하지 않는다 — 매번 다른 방식으로 그린 차트가 섞이면 자료를 신뢰할
수 없게 되고, 그게 표현을 한 곳에 위임하는 이유 자체를 무너뜨린다.

사용자에게 **pptx 스킬이 없어서 차트 없이 표로만 만든다고 먼저 알리고**, 어떤
형식으로 받을지 고르게 한다. 조용히 형식을 바꿔 내놓지 않는다 — 결과물을 어디에
쓸지는 사용자만 안다.

| 대안 | 만드는 법 | 어울리는 상황 |
|---|---|---|
| **(a) 워드 문서** | `python-docx`로 표 중심 조립 (`odoo-purchase-report`와 같은 방식) | 인쇄·결재·첨부 |
| **(b) 대화 내 표** | 마크다운 표로 바로 출력 | 지금 당장 숫자만 확인 |

판단이 서지 않으면 (a)를 권한다 — "대시보드"라는 말이 나왔다면 남에게 보여줄
자료일 가능성이 높고, 파일로 남는 편이 쓸모 있다.

차트가 꼭 필요하다면 우회하지 말고 **pptx 스킬 설치를 안내한다.** 설치 후 다시
부르면 1부의 데이터 수집부터 그대로 이어서 슬라이드를 만들 수 있다.

### 데이터는 재사용한다

어느 경로든 1부에서 모은 데이터를 그대로 쓴다. 형식을 바꾼다고 Odoo를 다시
부르지 않는다. 재조회하면 시간도 들고, 그 사이 데이터가 바뀌어 같은 대시보드
안에서 숫자가 어긋난다.

## pptx에 무엇을 넘기는가

차트는 이 스킬이 그리지 않는다. **완성된 이미지가 아니라 차트의 재료를 넘긴다** —
계열 데이터, 축 이름, 단위, 강조할 항목을 주고 그리는 일은 pptx에 맡긴다. 미리
그려서 그림으로 넣으면 슬라이드 테마와 따로 놀고, 나중에 수치를 고칠 수도 없다.

최소 두 장은 있어야 대시보드라고 할 수 있다:

- **재고 부족 품목** — 품목별 현재고 vs 최소재고 막대. 🔴/🟡 구분을 색으로 요청한다.
- **거래처별 발주 합계** — 금액 내림차순 막대. 집중도가 한눈에 보인다.

각 차트에 대해 pptx에 넘길 것:

| 항목 | 예시 |
|---|---|
| 차트 종류 | 가로 막대, 계열 2개(현재고·최소재고) |
| 계열 데이터 | `[{"품목": "SMPS-200", "현재고": 5, "최소재고": 20}, ...]` |
| 축·단위 | X축 "수량(개)", Y축 품목코드 |
| 강조 | 🔴 항목은 경고색, 🟡은 주의색 |
| 정렬 | 부족 수량이 큰 순 |

## 마무리

숫자만 놓고 끝내지 않는다. 대시보드를 보는 사람이 알고 싶은 건 결국 "그래서
지금 뭘 해야 하나"다. 마지막에 🔴 품목 발주, 미확정 견적서 처리처럼 **다음 행동
한두 가지**를 적는다. 실제 발주까지 진행하겠다면 `odoo-reorder-request`로 넘기고,
**발주 생성은 반드시 사용자 승인을 받은 뒤에** 한다.

## 하지 않는 것

- **차트를 이 스킬이 직접 그리기.** 차트는 pptx의 몫이다. pptx가 없으면 차트
  없이 표로 간다 — 다른 도구로 대신 그리지 않는다.
- **문서 서식을 이 스킬 안에서 직접 코딩하기.** 표현은 위임한다.
- **판정 기준 임의 변경.** 사용자가 명시적으로 바꾸라고 하지 않는 한 1단계
  기준을 그대로 쓴다. 기준이 바뀌어야 한다면 이 파일을 고친다.
- **쓰기 작업.** 발주 생성·재고 조정은 하지 않는다 — `odoo-reorder-request`의 몫이다.
- **품목마다 따로 조회하기.** 3~4회로 끝난다.
